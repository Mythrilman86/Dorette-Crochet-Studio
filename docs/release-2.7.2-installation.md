# Updating safely to v2.7.2 — proposed, not yet published

1. Save your work. Keep external backups of every kind you use: chart-library ZIP; Settings & Layout JSON; Written Pattern .deewritten files AND their original PDFs; Pattern Creator .deepattern files. A finished PDF is not an editable project backup. Keep older backups too.
2. Windows ONE-TIME transition from an older package: close saved Studio tabs, stop only the old Studio helper normally, retain its folder, and extract the verified new ZIP into a separate permanent folder. Open its Open Dee's Studio.cmd using the SAME Windows account and Edge/Chrome profile, at http://127.0.0.1:17828. Never substitute localhost or another port. Do not run old/new helpers together. File:// or production-website data are separate and require deliberate supported backup transfer; they will not automatically appear here.
3. Windows subsequently: close other saved Studio pages and use Save & Update when the compatible official application update is offered. Helper/launcher changes can still require another manual package transition. Do not assume every future release can update the immutable helper automatically.
4. iPhone: use the EXISTING production Safari context or Home Screen icon. Close other saved Studio pages. When notified, choose Save & Update once. Wait for running v2.7.2, Saved and Ready for offline use. Do not remove/reinstall the app or clear site data. Safari and Home Screen can hold different data; one does not synchronize the other.
5. Check familiar work before continuing. If anything is missing, saving fails or no safe update is offered, STOP with the existing app, data and backups intact. Do not retry, restore over data or use older code as an automatic rollback. Retaining old program files is not a guarantee of data-schema rollback.

Windows requires Windows 10/11 capable of running a supported current Edge/Chrome, native Windows PowerShell 5.1 and writable browser storage. Older Windows laptop compatibility remains unverified. No administrator permission or persistent execution-policy change is required. The existing launch/stop scripts DO use a temporary process-only ExecutionPolicy Bypass argument; this is disclosed rather than silently added or removed. It suppresses execution-policy warnings in those processes. Stop if organization policy or security software blocks execution; do not weaken protections.
