# Offline recovery and Written Pattern Companion integration audit

Baseline: published 2.4.1 Android Build 18, commit a9e6045b970e492ade524cdae87f200e89c4a7ef. Inputs: draft #19 at 07727c90444e44d70790a596bfa825889fb56389 and draft #20 at 80453cf08e4e1b090986478b9b2f5cb894acefb0. Both inputs passed their own CI. Neither source branch is updated by this candidate.

## Integration decisions

The service worker and web CI workflow conflicted. The integrated worker keeps the chart shell and adds the companion page, styles, modules and vendored PDF.js assets to the same cache. It uses a unique integration cache key. The old active cache is kept until the new worker has fetched its complete manifest and activates. A failed fetch can delay initial offline availability for both workflows. Test interrupted installation and upgrades on real devices before release. CI runs both Chromium regressions. The index page merged cleanly, with Written Patterns navigation and Project Protection preserved. Stable version metadata was restored, including the Android version code. Integration work does not create an installable production update.

## Data and backup boundaries

- Charts remain in dorette-crochet-studio, version 1, with project records and the category catalog. The chart owner lock and write queue remain in place. Project Protection stores bounded local snapshots in dorette-studio-local-recovery. The latest write can be lost if the process ends before transaction commit. Snapshot writes are best effort and may be skipped for quota, size or timing reasons.
- Written patterns live in dee-written-patterns, version 1, with separate document and metadata stores. Working-position saves use a revision check. Import, removal and restore update both stores in one transaction. The active-written-pattern preference is independent of the chart active-project key. The databases need no schema migration to coexist. All stores still share the browser origin quota and can disappear together if site data is cleared. Large PDFs may reduce the space available to charts and snapshots.
- Chart ZIP and .deewritten remain separate formats with separate pickers. Chart ZIP checks archive structure, CRC and records and restores new project IDs. The companion checks metadata and PDF SHA-256, validates page bounds, and restores under a new ID. These digests detect corruption and verify exact PDF reattachment. They do not establish who created a backup. A full-library chart ZIP excludes written patterns. Keep a separate independent companion backup for each pattern.
- External chart backup status is a user confirmation of a ZIP and a revision timestamp. Organization-only mutations may not advance the chart timestamp, so the status is not proof that pins, categories or Recycle Bin changes are covered. A download or share request alone does not verify an external file. Companion notes must be saved before exporting. A full companion restore still needs capacity for the original PDF bytes.
- Chart snapshots and companion documents share origin storage. Repeated imports or restores create separate copies and may use additional space. Large PDF decoding, portrait/landscape re-rendering, and low-quota behavior need longer physical-device runs. A local snapshot is not an independent backup.

## Platform and release gates

The production package remains com.deescrochetstudio.app and keeps its established signing configuration. Preview package com.deescrochetstudio.preview uses a different signing identity and private application storage. A production upgrade cannot see the Preview database. To move a pattern, export and verify its .deewritten backup in Preview and restore a copy in the eventual production release. Keep the Preview installed until the transfer has been verified. The existing native Android file bridge remains bundled with the reader. iOS CI validates packaging only. Safari and Home Screen offline behavior require manual validation. No native iOS distribution is planned.

Recommend 2.5.0 because written patterns are a new project workflow. Recommend production Android code 20 or higher after checking the latest released and privately distributed production-package builds. The #19 test APK already used code 19 under the production ID. The separate Preview code sequence does not constrain production.

Before publication, set release metadata on the approved candidate, build with the retained production certificate, test an in-place upgrade from exact stable 2.4.1 and any production-package test build still in use, and compare saved records. Verify both backup formats and Preview-to-production transfer on both Samsung devices. Test Windows and Safari/Home Screen separately, including an offline restart, interrupted cache installation, and low-quota error recovery in disposable data. Approve the exact signed bytes and source before merge, tag, Pages deployment, or distribution.
